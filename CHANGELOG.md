# Changelog

All notable changes to Pooled (called SwarmLLM before September 2026). Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Entries before the rename keep the old name.

## [Unreleased]

### Added
- **`@pooled/cli` 0.3.1: a first run that isn't clunky.** `pooled` alone opens a short menu in a terminal (Host a room / Join a room / Chat with a room / Use a room from your tools / Manage models; ↑/↓ and Enter or a number) and each item runs that flow; without a terminal it prints a 9-line usage. `pooled --help` is a 13-line overview with an example per command (the details stay under `pooled <command> --help`). A mistyped command or option is one line with the nearest real one (`pooled: unknown command "hsot". Did you mean "host"?`, also `jion`, `pul`, `models` -> `list`; `pooled host: unknown option "--gbb". Did you mean "--gb"?`) and a missing argument says what to type (`pooled serve needs a room: pooled serve 4TK-G9P, or paste the invite link in quotes.`): no more 30-line help walls. The GPU driver's own stderr lines when Dawn starts (`MESA: error: Opening /dev/dri/card0 failed`, `TU: error: … VK_ERROR_INCOMPATIBLE_DRIVER`, `Warning: maxDynamicUniformBuffersPerPipelineLayout artificially reduced …` on a GB10; all printed synchronously inside the first `requestAdapter()`) are hidden by pointing fd 2 at a file around Dawn's native calls and back (close + open takes fd 2 again; Linux and macOS), shown with `--verbose`, and quoted when no GPU is found. `pooled join` downloads the host's model to `~/.pooled/models` first (the pull progress bar) when it isn't there, instead of a long "loading layers 1%" while it streamed from Hugging Face; `--no-pull` streams, and the status line says what a load is doing (`downloading 312 of 900 MB · 18 MB/s · from Hugging Face`, `loading onto the GPU`). Pooled keeps its models in one folder, `~/.pooled/models`, made on first use and shown once on the host screen (`--models` / `POOLED_MODELS` are advanced overrides under `pooled pull --help`). The host screen shows the room's header once (code, invite link, the `pooled join` command, GPU and models folder, one privacy line) instead of twice, the model picker reads plainly ("22.8 GB · runs here alone", "needs 2+ devices", no footnote), and when the pledges split a model this computer could hold alone the panel says so before Start ("Qwen3 1.7B would run on spark alone if it lends 4 GB (now 2 GB): p raises it. Split across 2 devices, each token waits for the network: expect roughly 14 tok/s.", from the links' round trips), and the online line gives tok/s and the network's share. Fixed: `pooled chat`'s prompt could be redrawn over a streaming answer on a keypress or a resize (`def add_numbers(a, b):` came out as `>>> _numbers(a, b):`); the prompt now exists only between answers. The screens use plain ANSI (no terminfo), so they work over ssh from Ghostty (`xterm-ghostty`), in tmux, with `NO_COLOR`, and with `TERM=dumb` (numbered questions, one line at a time). A new look for the menu, `pooled host`, `pooled join`, `pull` and `chat`, in the site's language (`cli/lib/style.js`): the 3x3 dot mark, the room code as a blue pill, one accent (#2A45E0, #7F93FF on dark backgrounds; 256-color and NO_COLOR fallbacks, light or dark from OSC 11 / `COLORFGBG` / `POOLED_THEME`), thin `━` bars, words for states, key hints in the footer (`l` lends, `i` copies the invite link over OSC 52), no green/yellow/cyan. Streaming layers from Hugging Face (`--no-pull`, and a host that streams) is 4-5x faster: the room node plans the shard's byte ranges, merges them into chunks of up to 64 MB and fetches 6 at a time ahead of the loader, at most ~512 MB buffered (the 1.7B's layers 13-27, 765 MB on the Spark: 39-45 s -> 8.5-8.8 s); `pooled pull` downloads files of 64 MB or more in 4 ranges at once (resume per range from `<file>.part.json`; size and SHA-256 checked as before).
- **`@pooled/cli` 0.3.0**: `pooled pull` / `list` / `rm` and the interactive `pooled host` and `pooled join` (#270) ship on npm. The WebGPU addon (npm `webgpu` 0.6.1, ~95 MB) is now an optional dependency, so `npm i -g @pooled/cli` or `npx @pooled/cli host` works without installing it by hand; if it fails to install, `pooled serve` and `pooled chat` still work and `host` / `join` say how to add it.
- **OpenClaw plugin and a headless room node** [proof of concept, not published] (`packages/openclaw`, `@pooled/openclaw`; `packages/room-node`, `@pooled/room-node`). Pick Pooled in `openclaw onboard` ("Start a room on this device" or "Join a room") and the OpenClaw gateway becomes a device in a Pooled room: it runs its share of the layers with Pooled's own engine on Dawn (npm `webgpu`) in the same process, with WebRTC from node-datachannel, and browser tabs and phones on pooled.run join the same room. OpenClaw's requests, tool calls included, go through the same path as `pooled serve` (`cli/lib` request checks, `room/api.js` on the host, `cli/lib/answer.js` answer checks). The room node speaks the current protocol (serve v2, the faster-host pick, one submit per token, devices coming back into their slot, `ai-linked`, `ai-wake`); The node keeps the browser room's checkpoints (`packages/room-node/ckpt.js`): OpenClaw's system prompt + tools and its own STABLE cache boundary are pinned, answer states are kept by GreedyDual so session titles and compactions do not push out the conversation, and every session on the host shares them. On the 35B MoE split over two nodes on one GB10, OpenClaw's 11.3k-token first request takes 84 s cold; a new session then answers in 2.0 s, the next day's in 6.9 s, a follow-up in 0.3 s (answers identical to prefilling everything). The dense engine gets GPU slots for this (a browser host still keeps checkpoints to the qwen35 engine), and a node opens MoE rooms at 128k (27B at 64k), lowered to what the smallest GPU binding limit in the room holds, like a browser host (a node reports `maxBindMB` too). Fixed with it: after a single-token frame a worker's engine position stayed at that token, so a checkpoint saved before the next frame left out its KV row (both engines; batched frames were right). `cli/lib/room.js` Bridge takes an optional PeerJS class, so one process never loads two WebRTC stacks. Turn checkpoints: the host also saves the state where a prompt's last user turn starts, because OpenClaw ends every call with per-call context that the next call drops; each step of a tool loop now reads only its new tokens (Spark + Mac, OpenClaw's long-file task 813 -> 306 s, feature task 298 -> 139 s). `packages/room-node/join.mjs` lends a machine's GPU to a room from the command line. Real agent tasks on the MoE across a Spark, a Mac Studio and an iPhone: [docs/openclaw-poc.md](docs/openclaw-poc.md). Review fixes: closing a room node no longer counts its own links as departures (it used to arm the 60 s re-deal and reload the whole model on the closing machine); the node takes a `visibility` option and the plugin hosts with `asker`, so other devices' screens get the "answering…" stand-in instead of OpenClaw's prompts, answers and tool calls; API asks are only answered from devices that joined as API clients, and `allowApi` (plugin `allowApiClients`, `POOLED_ALLOW_API`) turns them off; host room codes are checked against the room page's alphabet; the plugin's state-file timer stops with its service and an abort before the ask is honored. Overview, setup on Linux and macOS, results and limits (including who can see and steer what in a room): [docs/openclaw.md](docs/openclaw.md).
- **Rooms at work: a default TURN relay** ([docs/rooms-at-work.md](docs/rooms-at-work.md)). When the site's owner sets a provider in the Vercel environment (Cloudflare Realtime TURN: `TURN_KEY_ID` + `TURN_KEY_API_TOKEN`; or coturn `use-auth-secret`: `TURN_SECRET` + `TURN_HOST`/`TURN_URLS`), `POST /api/turn` (api/turn.mjs) hands each device relay credentials that expire (6 h by default, refreshed by the page) for UDP 3478, TCP 3478 and TLS 443, so rooms connect on networks that block UDP. Links still go direct when they can; `?relay=1` forces the relay, `?relay=0` skips it. Only this site's own pages may ask (Origin check), with a per-IP limit. Model weights never go over a relayed link (both sides refuse; the device downloads them instead), so the relay only carries tokens. A device on a network that blocks UDP and has no relay says so (the join fails with the reason and a docs link instead of a generic error). Not configured: the room works exactly as before.
- **Rooms: 6-character codes and Allow / Deny for new devices.** New rooms get codes like `4TK-G9P` (30^6 instead of 30^4; four-character codes and `/r/ABCD` links of rooms opened before still work). A device that types the code waits ("Waiting for the host to let you in") until the host presses Allow on "otter wants to join (Mac, 8 GB)"; Deny sends it back with a message. The host's invite link and QR code carry a random key in the fragment (`/r/4TKG9P#k=…`) that lets a device in without asking, and a device the host let in comes back after a reload or a lock without asking again, also after the host reloads. Room settings: "Ask before new devices join" (on). `pooled serve` takes the invite link (or waits for Allow with the code alone). An older tab joining a newer host is told to reload; a newer tab joining an older host joins as before. `PROTOCOL` stays 4 ([docs/protocol.md](docs/protocol.md#joining-a-room)).
- **`pooled pull`, `pooled list`, `pooled rm` and an interactive `pooled host`** [preview] (`cli/`, on npm from 0.3.0). Like `ollama pull`: `pooled pull <model>` (alias `download`) downloads a model's GGUF (and the dense models' config and tokenizer) to `~/.pooled/models/<model>` (`--models` / `POOLED_MODELS`), with a one-line progress bar (size, %, MB/s, ETA; plain lines without a terminal), into a `.part` that resumes with a Range request after Ctrl-C or a dropped network, checked against its exact size and SHA-256 (new in room/models.js `FILES`, Hugging Face's own numbers) before it is renamed. `pooled list` (`ls`) shows what is here and what is not (with partial downloads), `pooled rm` deletes one; a part of a name works (`pull 35b`). The room node reads `<dir>/<model>/<file>` first, so `pooled host` and `pooled join` start from disk instead of streaming the layers from Hugging Face on every start (1.8 GB 1.7B pulled on the Spark at ~106 MB/s, SHA-256 checked). `pooled host [model]`: in a terminal the room opens at once (code and invite link at the top), then a model picker (each model's need over the room, downloaded or its download size, the one this GPU holds alone preselected; a model not downloaded downloads right in the screen while devices join), a pledge prompt (half the GPU by default, as the room page; ←/→ or type), and a live room panel redrawn in place: every device with its kind and pledge, the lobby (a / d), and whether the pledges hold the model with the room page's own math (room/plan.js `roomFit` over `roomBytes`, #271), "This room is X GB short for …" and Start off until they do; then each device's load progress, "online" with the layer split, and `c` to chat right there (pooled chat's REPL, `/exit` back to the panel). Every step has a flag that skips it (`[model]`/`--model`, `--gb`, `-y`, `--no-pull`, `--start`, `--wait N`, `--allow-all`, `--deny-unknown`, `--chat`, `--name`), so `pooled host qwen3.6-35b-moe --gb 64 --start --yes` asks nothing; without a terminal the room pulls a missing model first and starts once the pledges fit. `pooled join` alone asks for the code or link, shows the host's model and asks how much to lend (a node sends `pledge` as the room page does; a node host's hello names its model), and says once that `pooled pull <model>` makes the next join faster when it streamed. No new dependencies (a small terminal toolkit in `cli/lib/tui.js`, NO_COLOR respected). Driven through a pty on the Spark: pick Qwen3 1.7B, lend 2 GB ("1.8 GB short"), an interactive `pooled join` with the code alone waits in the lobby, `a`, the room fits, Enter, online in ~4 s; `pooled chat` and `c` in the host both answered (54 tok/s).
- **`pooled join`, `pooled host` and `pooled chat`: rooms from the terminal** [preview] (`cli/`, on npm from 0.3.0). `pooled join <CODE | link>` lends this computer's GPU to a room without a browser: the headless room node (`packages/room-node`, Pooled's engine on Dawn) holds the layers the host deals it, with a memory rule for how much to lend, a status line, reconnects (it knocks for a minute when the host link drops, rejoins only a host of the same name) and errors that say what to do. `pooled host` opens a room on this computer (Enter deals the layers, `--devices N` deals when N are in). `pooled chat <CODE | link>` talks to a room's model like `ollama run`: it joins as an API client over `pooled serve`'s bridge (v2 asks), streams the answer, keeps the conversation (each turn sends all of it, so the host's cache reuses the earlier turns: 34 of 60, then 70 of 92 prompt tokens reused on the Spark), shows reasoning dimmed (`/think`), `/clear`, `/exit`, Ctrl-C stops the answer being written, and prints room, model, tok/s and cache reuse under each answer; with a prompt or piped input it asks once, for scripts. Joining follows the room page's gate (#268, `room/joingate.js`): six-character codes (`4TK-G9P`, four still work), the invite link's `#k=` key lets a device in at once, a code alone waits in the host's lobby ("waiting for the host to let you in"), and the pass from the host lets it back in after a dropped link; `pooled host` prints the invite link, asks about each device that comes with the code alone (a / d in the terminal) and has `--allow-all`. Against a host from before the gate all three work as before. Qwen3 1.7B split over `pooled host` + `pooled join` on the Spark: 51-61 tok/s in `pooled chat`, Ctrl-C stops an answer in 0.2 s; Spark + Mac Studio with the 35B MoE: 45-53 tok/s ([cli/README.md](cli/README.md#talk-to-a-room-pooled-chat-preview)).
- **Room checkpoints on disk**: every device keeps a copy of its part of the room's checkpoints in OPFS, so a device or host that reloads reads it back and the next question resumes from the last saved answer instead of prefilling the whole conversation. A device lists the copies it read back when it says it is ready, and the host forgets any checkpoint a device lacks, so it prefills instead of asking for it. No new message; `?ckptdisk=0` turns it off.
- **`pooled serve`: a room as a local OpenAI and Anthropic endpoint** (roadmap 04, `cli/`, package `@pooled/cli`, not published yet). `npx @pooled/cli serve ABCD` joins the room as an API client with no layers and serves `POST /v1/chat/completions` and `POST /v1/messages` (streaming and not), `GET /v1/models` and `/health` on 127.0.0.1, so Continue, Open WebUI, LiteLLM, the `openai` / `anthropic` SDKs and curl run on the room's model. Requests share the room's one queue; a client's follow-up turn reuses the room's caches (exact sampled ids), so only the new turn is prefilled. `temperature`, `top_k`, `max_tokens`, stop sequences and thinking map onto the room's sampler (tool calling and the Responses API: next entry). Host and Origin checks against web pages, an optional token (`POOLED_TOKEN`). Prompts go to the room's host and follow the room's visibility (see cli/README.md, "Who sees your prompts").
- **`pooled serve` 0.2.0 [preview]: Chat Completions, Responses and Messages with tool calling**, so coding agents run on a room: Codex CLI (Responses, custom `apply_patch` included) reads a file with its own tool on Qwen3.6 35B MoE and Qwen3 1.7B, and Claude Code (Messages) on the MoE (its ~15 k-token prompt leaves the 1.7B's 16 k context too little room). On all three APIs: function tools (up to 1024), every `tool_choice` form, parallel calls, streamed call arguments, tool results, reasoning carried through the history (Anthropic thinking signatures and Responses `encrypted_content` hold it), JSON mode and JSON schemas. Every call and structured answer is constrained to its schema by a grammar on the room's sampler, for Qwen3's JSON calls and Qwen3.5+'s XML calls, so it always parses. Responses adds `previous_response_id` and stored responses (in memory, an hour). Images become a note; `max_tokens` defaults to 16384 and is capped at 65536; the banner, `/health` and `/v1/models` give the room's context and the Codex / Claude Code settings for it. No legacy `/v1/completions`. Protocol: a v2 `ai-ask` with `ai-call` messages, negotiated through the host's `hello` (an older host keeps answering plain requests; an older bridge keeps working); `PROTOCOL` stays 4 ([docs/protocol.md](docs/protocol.md#api-clients), [docs/design/serve.md](docs/design/serve.md) 11-15).
- **In the room**: API clients get their own card ("API client · Continue") and are not counted as devices; the host can disconnect one or switch API clients off; the black **Serve API** button in the room's header (the one with the dots) opens the Serve API page: this device's layers and passes beside the command for the room, the base URLs, examples and who is connected; once a client is connected the steps fold under "How to connect" and the page leads with what it serves ("Serving Continue via API · 12 requests answered"). API exchanges show in the chat marked "via API · not part of this chat's memory" and follow the room's visibility (the asking client always gets its whole answer). Protocol: new fields on existing messages, `PROTOCOL` stays 4 ([docs/protocol.md](docs/protocol.md#api-clients)).

### Changed
- **128K context on the 35B MoE** (`?ctx=131072`, was 64K): a needle is found at 32K, 64K, 96K and 128K on the GB10. A cold 128K prompt takes ~15 min to prefill there, so it is for sessions that reuse their checkpoints. The 27B goes up to 64K (was 32K). Each device reports its GPU binding limit and the host keeps the room's context within it; the engine refuses a KV buffer a device cannot bind with a readable error.
- **Code mode can run on `pooled serve`'s core** (`?hcore=1`, opt in: on the Code mode eval it holds on Qwen3.6 35B MoE, 19/24 against 18/24, and is faster there, but Qwen3 1.7B drops from 4/24 to 2/24 on the template's tool wording): every step goes through the same in-process code that answers API clients: the model's own chat-template tool prompt, the strict tool-call grammar (tool names and typed arguments, required parameters enforced), the streaming call parser and the room's exact-id reuse. History is kept as content plus calls, so a session renders right for either call style and survives switching back (`?hcore=0`). A cut `write_file` still keeps its complete lines, calls written outside the format still run with a hint, and a model failure now shows as an error instead of ending the request quietly. The eval runner gets `--codemode`, `--dense`, `--hcore 0|1`, `--sampling` and `--label` ([docs/design/harness-core.md](docs/design/harness-core.md)).
- **Code mode keeps the system prompt cached through compaction** (#73): the prefill pauses after the system prompt + tools and saves a checkpoint there (on every device in a room; it is never evicted by the answer checkpoints), so when compaction rewrites old turns the next step prefills only what follows it instead of the whole prompt. Same tokens at the same positions, so answers do not change. The eval runner shows tokens reused next to tokens prefilled for each task.
- **Rooms with phones** (device matrix, Spark + M5 Max + iPhone 14 Pro Max):
  - The layer split now defaults to **For speed**: the fastest devices fill first, each up to what it lends, and devices that aren't needed join to ask. Before the first answer measures each device, computers go before phones (an unmeasured phone counts as 20x slower), so a phone only takes the layers the computers can't hold. By memory is still in the room settings; `?split=memory|speed` picks one at load (the test harnesses pin `memory`).
  - A room split by memory no longer gives a phone layers when the other devices can hold the model; the phone joins as an ask-only guest (`?phonelayers=1` restores the old split). Qwen 3.6 35B on a GB10 + iPhone room: 1.6-1.9x faster, the same speed as the GB10 alone.
  - Keep-alive while an answer runs: each end sends 1 byte every 10 ms of silence on its own unordered channel (id 78), so Wi-Fi power save doesn't park the radio between laps. No protocol bump; `?ka=0` turns it off. Qwen3 1.7B, GB10 + iPhone: +17% plain.
  - Test rig for rooms with the iPhone (`tests/e2e/xroom_phone.mjs`, `xroom_cluster.sh`) and the measured matrix in docs/bench-log.md.
- **Metal (Apple GPUs)**:
  - The MoE's default prompt processing (wide prefill at ubatch 256 plus grouped experts) no longer loses the device under Deno on an M5 Max. Wide prefill now submits every 8 layers, which also makes GB10 MoE prefill about 5% faster, with bit-identical results.
  - Apple GPUs in Chrome and Safari get wider fused MoE expert kernels (`moeFusedLayout`; M5 Max kernel time: gate/up 0.49x, down 0.55x). Qwen 3.6 35B decode in Chrome on an M5 Max: +5.6% plain (86.1 -> 90.9 tok/s), +11% spec.
  - `moe_route` is 1.6-1.9x faster on every GPU (GB10 and M5 Max) and gives the same bits.
  - Other GPUs keep their output bits. MoE output on Apple still matches llama.cpp, and spec == plain.
- **First run, accessibility and speed**: a laptop alone now gives the 4 GB the smallest model needs (and a short room offers "Give N GB from this device"), Start says what it will download, a Start/Join tap made before the room script loads is kept, and the landing page and join screen say what a room needs; the room is a labelled radio group with real headings, a live-announced conversation and AA contrast, and the landing demo has a Pause button; the room no longer loads the inference engine or blocks on PeerJS before the join screen works (JS before join 271 -> 135 KB, fonts self-hosted), Lighthouse accessibility 91 -> 100 (landing) and 98 -> 100 (room).
- **The model host is the device whose GPU moves memory fastest**, when it is clearly faster (1.5x a copy's GB/s, measured at page load in `room/gpuspeed.js`, about 12-450 ms) and lends at least half the memory of the device that would host by memory. Before, it was the device that lent the most memory. GB10 + M5 Max room (the Mac copies at about 390 GB/s, the GB10 at about 190): the Mac hosts, and the MoE's speculative decode is +20-39% (plain +9-11% on a calm link), the 27B's speculative +17-19% (plain unchanged). Same tokens for a given split; the GB10 alone is unchanged. `?gbps=N` pins the value (0 = unknown, which leaves the pick by memory).
- **A room's host runs its share of each lap in one GPU submit** (engine `hostFuse`): in plain greedy decoding the head of the returned hidden, the pick's embedding and the host's layers on it are one command buffer with one readback, and a speculative step's draft chain, draft embeddings and host layers are another. GB10 host + M5 Max guest, MoE over Wi-Fi: plain +7-11%, speculative two-sum +4.5%. Same kernels in the same order, so the same tokens; one device is unchanged. `?hostfuse=0` for A/B.

### Fixed
- **Code mode cards in call order**: when one answer holds several tool calls, each call's card now takes the place of its own live card, so a "skipped: the same call as the one before it" card no longer shows above the call that ran (host and peers).
- **`pooled serve` and Code mode on a model with draft tokens (Qwen3.6 MoE)**: after the answer's end token, the tokens a speculative step writes to the caches are no longer masked by the tool-call grammar, so the next turn reuses the cached conversation instead of prefilling it again from the system prompt (8 re-prefills to 0 on a 6-task Code mode check).
- **Rooms never use more memory than a device pledged.** A laptop hosting Qwen3 1.7B with 3 GB next to an iPhone with 1 GB held all 28 layers (~3.7 GB) and the phone none: the deal counted a dense layer's weights (51 MB) but not its f32 KV cache (64 MB at 8k context), nor the host's second copy of the embedding, so the laptop's 3 GB "held" 54 layers. The deal now counts both (Qwen 3.5+: the draft chain's copy of the embedding too), and neither split spreads layers past a pledge when a room is short (both used to, by capacity). The same room now deals laptop 21 layers (2.97 of 3 GB) and iPhone 7 (0.79 of 1 GB). A room whose pledges can't hold a model keeps Start off and says "This room is X GB short for <model>. Add a device or raise a pledge: Laptop could give X GB more"; a device left out says why on its card and Lend screen ("Not needed: the computers hold the model", "joined after the start: waits for a re-deal"); the pledge box says what a pledge covers.
- **`pooled serve` 0.2.1: the banner's agent settings match the room's model**: a bridge that joined before the host started the model printed Codex / Claude Code settings for a stale context (2048 tokens) and none once the model was ready; they now appear only when it is ready, and again when its context changes. The banner also prints a ready-to-paste opencode provider (`opencode.json`; setup and tips in cli/README.md), and the bridge log gives a tool-call turn's finish reason as `tool_calls` instead of `stop`.
- **iPhones in rooms no longer crash while downloading their layers** (#207). Measured on an iPhone 14 Pro Max (iOS 26.6): Safari gives a tab a 1536 MB soft limit (WebGPU buffers count against it) and its networking process 840 MB; after back-to-back loads the tab was killed at 1534-1537 MB. The crash came from downloads the tab never read, which piled up in Safari's networking process until iOS killed it and the page with it.
  - The prefetcher no longer downloads tensors that are already loaded, and cancels what nobody read when a load ends (a MoE layer wasted about 450 MB this way).
  - Weights taken from another device in the room stream with flow control (at most 8 MB in flight, new `ai-wack` message) instead of being buffered whole in JS; the sender streams from its cache, and desktop cache writes stream too. Q4_1/Q5_0/Q5_K/Q6_K tensors convert a few rows at a time on their way to the GPU (same bytes). A phone-shaped tab taking its layers from another device peaked at 307 MB, against 505-546 MB before.
  - Phones and tablets lend what their tab survives: iPhones and iPads 0.5 GB by default and at most 1 GB (the host also holds them to it, older code included); Android by `navigator.deviceMemory` (0.5 GB up to 2 GB of RAM, 1 GB below 8, 2 GB at 8, 1 GB when unknown). The Lend screen and the join box say why.
  - A device whose tab is killed while it loads gets a smaller share on its own re-deal (about half, new `ai-share` message); a second kill, or one at a single layer already, re-deals without it and it stays to ask.
- **A phone that locks, goes to the background or reloads comes back into its slot** (#207): every device holding layers keeps the screen awake (Screen Wake Lock, a sun in the header shows it), a phone back from the background reconnects by itself and keeps its layers when its slot is unchanged, a reloaded tab rejoins under its name, and an answer or Code run waits for the device and carries on from the last token shown. If it is not back within 60 s the host re-deals over the devices still there (the "Re-deal on its own" setting, experimental). iPhone, 30 s in the background: back and answering in 67 s with no download; reload: 53 s.
- **Phone GPU wake**: the host tells a phone worker when a decode lap starts (`ai-wake`), and the phone keeps its GPU clocked up until its frame arrives. Qwen 3.6 35B, GB10 + iPhone: +4.6% and +11.6% over two runs, same answers; `?wake=0` turns it off.
- **Rooms on bad networks**: signaling falls back through a list of servers (`window.POOLED_SIGNAL_SERVERS`, or `?signal=` as a comma list; the public PeerJS cloud stays the default), keeps reconnecting after a blip so new devices can join again (before, the host's registration never came back), and says so on the join screen when no server answers ([docs/self-host-signaling.md](docs/self-host-signaling.md)). Late frames on lossy links are waited for instead of skipped after 5 s, and small frames go out twice (15% loss: 1.4 -> 4.1 tok/s, 5%: 4.4 -> 7.3, Qwen3 1.7B on 3 devices). The host shows within 3.5-5 s which device stopped responding mid-answer and holds the answer for it. A dead link is redialed with the same layers, and an optional TURN relay (`?turn=`, the Network box) helps behind strict NATs. No protocol bump: `ai-linklost` is new, and older hosts ignore it. Before/after table in [docs/bench-log.md](docs/bench-log.md).
- **Room chat: emoji and non-Latin text no longer show broken characters (U+FFFD)** while an answer streams: a character split across two tokens is sent once it is whole.

## [0.2.0] - 2026-09-07

Demo release: Qwen 3.8 27B across a MacBook and an iPhone in browser tabs at 10.7 tok/s.

### Added
- Room topology is linear, not a mesh: every device keeps one link to the host; chain neighbours connect only when the layers are dealt (`ensureLink`). A 64-device room opens 126 links instead of 2,016. Workers draw the device list from the host's roster. `?signal=host:port` points the room at a self-hosted PeerServer.
- Room emulator (`npm run e2e`): `--devices N --phones K`, local PeerServer, 27B from local disk, room-log error capture, fail-fast on load errors. 16 devices on the 27B verified on GB10.

On a 100 ms link a token's hidden state now crosses a hop in 51 ms instead of 152, and a depth-5 verify block in 52 ms instead of 355 (docs/bench-log.md, transport section). Bytes only, output unchanged.
- Multi-token-prediction speculative decoding using the model's built-in draft layer; output is bit-identical to plain decoding. Solo host and device chains.

- Batched prefill: 4 (now up to 8) tokens per GPU pass, 16 tokens per network round.
- Device autotune for the cooperative GEMV shape at load.
- Binary WebRTC frames and f16 wire format for activations (one third of the original bytes per hop).
- Fused gate/up GEMV with in-kernel SiLU; fused DeltaNet gate + L2-norm pre-pass; accumulate-into-residual matvec variants.
- Bench log, kernel-family profiler, GEMM prefill prototype, research plans and four implementation designs under `docs/` and `docs/research/`.
- A roadmap (`roadmap/`) of 27 items, each mirrored by a tracking issue.
