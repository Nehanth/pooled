Every performance claim in Pooled comes with the hardware and the commit that produced it. There are two ways to contribute numbers:

- **Reporting a device we don't have:** use the benchmark issue template. This is one of the most useful things you can send.
- **A pull request that changes speed:** add a row to `docs/bench-log.md` with before and after numbers.

## Report numbers from your hardware

You don't need to clone anything. Open a room on [pooled.run](https://pooled.run/room), load a model, and ask one of the standard prompts below twice. Then [open a benchmark report](https://github.com/Nehanth/pooled/issues/new?template=020-benchmark-report.yml) with:

- **Hardware**, for example `MacBook Pro M4 Max 64 GB`, `RTX 4090` or `Pixel 9`;
- **Browser or runtime, and its version**;
- **Commit or site build**, for example `pooled.run on 2026-10-11`;
- **Numbers:** the model, the room size, whether the devices were on the same network, prefill and decode tokens/s (plain and speculative if shown), and the breadcrumb line.

Report the second answer or a later one. The first answer in a room is slower, because speculative decoding starts cautious.

## Standard prompts

Room numbers can only be compared when the prompt is the same. Use one of these, word for word, and name it in your report:

| Name | Tokens | Use it for |
|---|---|---|
| `hello` | 1 | Fixed per-request overhead |
| `meaning` | 6 | Fixed per-request overhead. The text is `what is the meaning of life`. |
| `japan` | 160 | Any claim about prefill. It is long enough to run through the 16-column prefill path. |

Token counts are for the Qwen 3.8 27B tokenizer, text only. The chat template adds about 9 more. The full `japan` text is in [`docs/bench-log.md`](https://github.com/Nehanth/pooled/blob/main/docs/bench-log.md#standard-prompts). Decode numbers use the 400-token answer cap.

## Measure a change

Pick the harness that matches what you changed. All of them need a GPU, and none of them should run while another GPU job is running.

<Tabs>
<TabItem label="Engine (Deno)">
```bash
npm run bench                       # Qwen3 0.6B: prefill and decode tok/s
npm run bench:q38                   # the full 27B, with the room's settings
TOKENS=128 npm run bench:q38        # time more decode tokens (default 32)
ROOM_FLAGS="kv=q8" npm run bench:q38   # the same with a room switch
```

For context length and per-kernel time:

```bash
cd tests
D="deno run --unstable-webgpu --allow-read --allow-env --allow-write=$HOME/.cache/swarmllm-weights"
MODEL=moe FILLS=1024,4096,16384 $D bench_ctx.js   # prefill and decode against context fill (MODEL=27b for the dense)
Q38=1 $D prof_ts.js                              # per-kernel GPU ms (drop Q38 for the MoE)
```
</TabItem>
<TabItem label="Chrome">
The numbers we quote for browsers come from a real Chrome page with the real GPU:

```bash
node tests/bench/chrome_bench.mjs models/q36moe/Qwen_Qwen3.6-35B-A3B-Q4_0.gguf
```

After the model path, an optional second argument sets the number of decode tokens (default 40) and a third adds page options, for example `"ubatch=256&prefilllen=2048"`. Loading is kept out of the tokens/s numbers. The first run fills a converted-weights cache and later runs load faster. Set `WCACHE=0` or `CHROME_PROFILE=0` to measure a cold load.
</TabItem>
<TabItem label="Rooms">
One machine, several headless Chromium tabs, with emulated network latency:

```bash
node tests/e2e/room_latency.mjs --model qwen3.6-35b-moe --devices 2 --lat 0,5,20 --maxnew 128
```

The latency is added in the page. It holds every hidden-state frame back for the given time, but it doesn't model bandwidth or packet loss. For real links, use `tests/e2e/xroom_pair.sh` across two machines (see [Testing](/docs/contributing/testing#real-devices)).
</TabItem>
</Tabs>

<Aside type="tip">
Profile by leaving kernel families out, not with GPU timestamp queries. Just turning timestamp queries on made everything about 3 times slower. A traced room round is useful for splitting time between compute and the wire, but don't quote its tokens/s.
</Aside>

## Add a row to the bench log

Any PR that claims a speed change adds a row to [`docs/bench-log.md`](https://github.com/Nehanth/pooled/blob/main/docs/bench-log.md), and neutral results count too. A row names:

- the date and the change;
- the commit;
- the hardware and the runtime (Deno or Chrome, and the GPU);
- the before and after numbers;
- anything that makes the numbers hard to compare.

If you measured in a room on real devices, also add a row to the **Room benchmarks by PR** table. "Before" is production (`main`) on the same day, and "after" is the PR's preview URL. Prefill is the seconds the status line reports, and decode is the tokens/s in the answer's footer. Name the devices and the standard prompt.

Output must stay bit-exact. A faster kernel counts only if the golden tests still pass and the speculative stream still equals plain decoding.

Summaries of the headline numbers are on [Benchmarks](/docs/internals/benchmarks).
