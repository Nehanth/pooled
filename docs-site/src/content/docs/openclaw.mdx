[OpenClaw](https://github.com/openclaw/openclaw) is a self-hosted agent: a gateway process on your machine runs the agent loop and its tools (`exec`, `read`, `edit`, …) and calls a model provider for every step. The `@pooled/openclaw` plugin adds **Pooled** as that provider.

When you pick Pooled, the OpenClaw gateway itself becomes a device in a Pooled room. It holds its share of the model's layers on the local GPU and runs them with Pooled's own engine, on Dawn (npm `webgpu`) inside the gateway's Node process. Other devices join the same room and hold the rest:

- another machine with the plugin, or with [`pooled join`](/docs/terminal);
- a browser tab or a phone with the room's invite link.

So a model none of the devices can run alone serves the agent, with no API key and no cloud model.

```text
 OpenClaw gateway (Spark)                Mac Studio               iPhone (optional)
 ┌───────────────────────────┐          ┌──────────────┐          ┌──────────────┐
 │ agent loop + tools        │          │ pooled join  │          │ Safari,      │
 │ @pooled/openclaw          │  WebRTC  │ Node + Dawn  │  WebRTC  │ pooled.run   │
 │ room node: embed, layers  │ <------> │ layers 19-39 │ <------> │ 1-2 layers   │
 │ 0-18, head, checkpoints   │          │ (Metal)      │          │              │
 └───────────────────────────┘          └──────────────┘          └──────────────┘
```

OpenClaw's requests and tool calls take the same path as [`pooled serve`](/docs/serve): the room's host renders the chat template, constrains tool calls with a grammar and parses them. The host also keeps OpenClaw's system prompt and each turn as checkpoints, so each step reads only its new tokens.

## Install

You need Node 22 or newer (OpenClaw ships on 24), OpenClaw 2026.9.6 or newer, and a GPU that Dawn runs on: Linux with glibc 2.38 or newer and a Vulkan driver, or macOS 26 or newer. Windows is untested.

```sh
openclaw plugins install @pooled/openclaw
openclaw onboard          # Model/auth provider -> More... -> Pooled
```

- OpenClaw asks you to confirm a package from npm and to accept its capabilities; `--force --accept-capabilities` skips both.
- `webgpu` (Dawn, about 95 MB) is an optional dependency. If it didn't install, the gateway says how to add it when it needs the GPU.

### From a checkout

```sh
git clone https://github.com/Nehanth/pooled.git && cd pooled/packages/openclaw
npm install && npm pack
openclaw plugins install ./pooled-openclaw-0.2.0.tgz --force --accept-capabilities
```

## Start a room

In `openclaw onboard`, pick **Pooled** → **Start a room on this device**, then:

1. Say how much of this GPU's memory to lend.
2. Pick the model. Each one shows whether it's downloaded, its download size, the memory it needs across the room and its context; the one this machine holds alone is recommended. The Qwen3.6 35B MoE is the one for agent work.
3. If it isn't downloaded, pick **Download now**, **Download when the gateway starts** or **Don't download** (stream this machine's layers at each start).
4. Pick how many devices to wait for, and who can join: **Devices with the invite link** or **Anyone with the room code**.

Onboarding prints the room code (`4TK-G9P`) and the invite link (`https://pooled.run/r/4TKG9P#k=…`). The room opens when the gateway starts and keeps its code and link across restarts. On your other devices, do one of these:

- Open the invite link in Chrome or Safari.
- Run `npx -p @pooled/cli -p webgpu@0.6.1 pooled join "<invite link>"`.
- Pick **Join a room** in OpenClaw there and paste the link.

## Join a room

In `openclaw onboard`, pick **Pooled** → **Join a room**, paste the invite link (or type the code) and say how much memory to lend. Onboarding connects right away:

- With the invite link, the device is let in at once.
- With the code alone, it shows `Waiting for <host> to let this device in…` until the host allows it.

It keeps the pass the host gives it, so the gateway gets straight back in after every restart. It also learns the host's model and context window.

The room needs at least a 16k context, because OpenClaw's own instructions and tools are about 12k tokens. `pooled host qwen3-1.7b` opens at 8k, so its host should run `pooled host qwen3-1.7b --ctx 16384`. Onboarding warns when the context is shorter.

## Let devices in: /pooled

In any OpenClaw chat (the TUI, the Control UI, a messaging channel), the gateway's owner can run:

| Command | What it does |
|---|---|
| `/pooled` | Shows the room: invite link, devices, whether they hold the model, who is waiting to join |
| `/pooled allow` | Lets the first waiting device in (`/pooled allow 2`, `/pooled allow all`) |
| `/pooled deny` | Turns it away |
| `/pooled link` | Prints the invite link |
| `/pooled pledge 12` | Lends another amount of this machine's GPU memory |

## Models

Models are kept in `~/.pooled/models`, the same folder as [`pooled pull`](/docs/terminal), so each is downloaded once per machine. Downloads resume and are checked against their SHA-256. A hosting gateway downloads a missing model in the background while devices join; a question meanwhile says how far it is.

## Config

Onboarding writes `plugins.entries.pooled.config`. Each key can be overridden by its variable:

| Key | Variable | Meaning |
|---|---|---|
| `mode` | `POOLED_MODE` | `host` or `join` |
| `code` | `POOLED_CODE` | The room code |
| — | `POOLED_LINK` | A room's invite link, to join (non-interactive setup) |
| `model` | `POOLED_MODEL` | The model a host starts |
| `pledgeGB` | `POOLED_PLEDGE_GB` | GPU memory this device lends |
| `minDevices` | `POOLED_MIN_DEVICES` | Devices to wait for before dealing the layers (default 1) |
| `ask` | `POOLED_ASK` | Host: a device with the code alone waits for `/pooled allow` (default on) |
| `pull` | `POOLED_PULL` | Host: download a missing model (default on) |
| `prewarm` | `POOLED_PREWARM` | Host: warm up OpenClaw's system prompt and tools when the room comes online (default on) |
| `allowApiClients` | `POOLED_ALLOW_API` | Host: answer other devices' API asks (default on) |
| `modelDir` | `POOLED_MODELS` | Models folder (default `~/.pooled/models`) |
| `waitSeconds` | `POOLED_WAIT_S` | How long a question waits for devices or the host's model (default 120) |
| `ctx` | `POOLED_CTX` | Context to ask for (default: the model's largest) |
| `name` | `POOLED_NAME` | This device's name in the room |
| `signal` | `POOLED_SIGNAL` | A PeerServer `host:port` (default: the PeerJS cloud server pooled.run uses) |

Non-interactive setup: `openclaw onboard --non-interactive --auth-choice pooled` with `POOLED_MODE=host`, or with `POOLED_LINK="<invite link>"` to join.

The invite key and the passes are kept in `~/.openclaw/pooled/room.json` (mode 0600), never in `openclaw.json`.

Room problems show in the OpenClaw chat as `⚠️ Pooled: …`: waiting for the host to let this device in, waiting for devices, not enough memory, downloading, a device left while it held layers, the host doesn't allow API clients, the host runs an older Pooled. The model never sees them. When the conversation outgrows the room's context, OpenClaw compacts it and asks again.

## Results

Qwen3.6 35B MoE (Q4_0, about 20 GB), 128K context, OpenClaw 2026.9.7 with its full tool profile. Five tasks, each in a new session, each checked by a script the agent never sees:

1. answer a question by reading files;
2. a code edit;
3. run the tests and fix the code;
4. add a feature with tests;
5. summarize a 140 KB (about 33K-token) file.

No tool call in any run was malformed or came back as an error.

| Room | Layer split | Passed | First call (cold) | Decode |
|---|---|---|---|---|
| A: OpenClaw on the Spark, Mac joins | Spark 0-18 + head, Mac 19-39 | 4/5 | 61.8 s (17.4K tokens) | 17-29 tok/s |
| A2: A with turn checkpoints | same | 5/5 | 61.7 s | 16-30 tok/s |
| B: OpenClaw on the Mac, Spark joins | Mac 0-18 + head, Spark 19-39 | 4/5 | 49.2 s (14.5K tokens) | 17-32 tok/s |
| C: A plus an iPhone 14 Pro Max in Safari | Spark 0-17, iPhone 18-19, Mac 20-39 | 4/5 | 89.2 s | 9-16 tok/s |

- After the first call, each task's first model call reads 4-8 s of prompt: the system prompt comes from a checkpoint.
- With turn checkpoints (A2), the four short tasks took 55-139 s and the long file 306 s.
- Every failure is the same model mistake on the edit task: it printed `$-12.34` instead of `-$12.34`, said it was fixed and never checked. In A2 the model tested its change and passed.
- The phone held its 2 layers through a 23-minute run and roughly halved the speed. A phone should get layers only when the computers can't hold the model.

**Turn checkpoints.** OpenClaw drops each call's trailing context block from the next call, so in a tool loop the host's cache never matched past the system prompt. The host now also saves a checkpoint where the last user turn starts. From A to A2: the long file went from 813 to 306 s, the feature from 298 to 139 s, the tests from 119 to 57 s.

Per-task tables are in [docs/openclaw-poc.md](https://github.com/Nehanth/pooled/blob/main/docs/openclaw-poc.md).

## Limits

- **Cold first call.** The first call after a gateway starts reads OpenClaw's whole prompt (14-18K tokens): 49-64 s on two computers, 89 s with a phone. A hosting gateway replays the last system prompt and tools when its room comes online, so that read happens before the first question. Checkpoints live in GPU memory only.
- **Decode over the network.** Two computers over Wi-Fi decode at 25-30 tok/s; the Mac alone does about 92. Splitting pays one network hop per token, so it is for models that don't fit on one device.
- **Browser hosts** have no turn checkpoints yet, so OpenClaw joined to a room hosted in a tab re-reads more per tool call.
- **Checkpoint memory** isn't part of the layer split. At 50K tokens one checkpoint is about 1 GB across the room for the MoE, and the host keeps up to 8 (4 pinned, 4 answer or turn).
- **Small models** (the 1.7B) get a file-tools-only profile; onboarding sets it. The MoE is the model to use.
- **Windows** is untested.

## Who can see and steer what

:::caution[Use rooms of your own devices]
Share the invite link only with people you trust, and keep OpenClaw's approvals on for `exec` and writes.
:::

- **Getting in.** A hosted room asks before new devices join: the invite link gets a device in, a code alone waits for `/pooled allow`, and a device you let in keeps a pass. With **Anyone with the room code**, anyone who has or guesses the code gets in.
- **Screens.** A hosting gateway opens its room so the other devices' room pages show "answering…" stand-ins, never OpenClaw's prompts, answers or tool calls.
- **Devices holding layers see the conversation anyway.** Each one gets the hidden state of every token, which carries the prompt (the files OpenClaw read, the tool results). A device holding layers can also send back any hidden states it likes. That lets it choose the model's output, **including the tool calls OpenClaw then runs on the gateway machine**. The call grammar only keeps the calls well formed.
- **Join mode trusts the room's host with everything.** It sends OpenClaw's whole context to the room's host and runs the tool calls it gets back.
- **Guests** can ask their own questions, which queue with OpenClaw's requests. Turn `allowApiClients` off to keep API clients out.

See also [Rooms from the terminal](/docs/terminal), which uses the same headless room node, and [Privacy](/docs/privacy).
