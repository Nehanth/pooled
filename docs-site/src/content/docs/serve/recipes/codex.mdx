<Steps>

1. Start the bridge for your room:

   ```bash
   npx @pooled/cli serve ABCD
   ```

   Wait for the line `For this room's N-token context:`. The Codex line under it has the two numbers you need.

2. Add a Pooled provider to `~/.codex/config.toml`. Use the numbers from the banner. This example is for a 32768-token room:

   ```toml title="~/.codex/config.toml"
   model = "pooled"
   model_provider = "pooled"
   model_context_window = 32768            # the room's context
   model_auto_compact_token_limit = 26214  # 0.8 of it

   [model_providers.pooled]
   name = "Pooled"
   base_url = "http://127.0.0.1:8080/v1"
   wire_api = "responses"
   ```

3. Run `codex` in your project as usual.

</Steps>

## Why the context lines matter

Codex has no size on record for a model it does not know. Without `model_context_window` and `model_auto_compact_token_limit`, it never compacts. The conversation keeps growing until the room refuses a prompt that is too long (a `400`).

The compact limit is 0.8 of the context, which leaves room for the next answer. For the numbers for each model, see [Context settings](/docs/serve/recipes#context-settings-for-coding-agents).

## Pick a room that can run Codex

Codex's own prompt is about 15,000 tokens before any history. Use a room with a long context and a model that calls tools reliably:

- **Qwen3.6 35B MoE:** works. 32K by default, up to 64K with `?ctx=65536`.
- **Qwen3.8 27B:** use it at 32K (`?ctx=32768`).
- **Qwen3 1.7B:** not reliable. It is capped at 16K, and under Codex's prompt it often says what it would run instead of calling the tool.

## Patches with a GPT-5 model name

With `model = "pooled"`, Codex prints a "model metadata not found" warning. If you set a GPT-5 model name instead, Codex sends its `apply_patch` tool as a custom (free-form) tool. The bridge supports custom tools, so that works too:

```toml title="~/.codex/config.toml"
model = "gpt-5-codex"   # also silences the "model metadata not found" warning
```

The room still answers with its own model. Only the name Codex sends changes.

## Slow rooms and the idle timeout

Codex gives up on a stream that stays silent for 5 minutes (`stream_idle_timeout_ms`, 300000 by default). While the room is busy or processing a long prompt, the bridge sends a `response.in_progress` event every 10 seconds, which resets that timer.

If a first prompt still takes more than 5 minutes, for example on a room of phones, raise the timeout in the provider section:

```toml title="~/.codex/config.toml" ins={5}
[model_providers.pooled]
name = "Pooled"
base_url = "http://127.0.0.1:8080/v1"
wire_api = "responses"
stream_idle_timeout_ms = 900000
```

## With a token

If you started the bridge with `POOLED_TOKEN`, tell Codex to send it as the API key:

```toml title="~/.codex/config.toml" ins={5}
[model_providers.pooled]
name = "Pooled"
base_url = "http://127.0.0.1:8080/v1"
wire_api = "responses"
env_key = "POOLED_TOKEN"
```

Export `POOLED_TOKEN` in the shell where you run `codex`.

## What to expect

- Codex always sends a `web_search` tool. The bridge skips it and logs one warning. Codex's other tools work.
- Thinking is off unless Codex asks for a reasoning effort.
- Without its own output limit, Codex gets up to 16384 tokens per answer, capped by the room's context.
- Each step after the first reuses the room's caches, so only the new tool results are processed.

<Aside type="note">
Tested with Codex CLI 0.104 on the Qwen3.6 35B MoE and the Qwen3 1.7B. On the MoE, Codex ran `cat a.txt` through its shell tool and quoted the file in 20 seconds.
</Aside>
