A room links its devices directly with WebRTC, over UDP. Work, school and hotel networks often block UDP and every port except 443. Then there is no direct path between two devices.

A **TURN relay** gets around that. Both devices reach the relay over TCP or TLS on port 443, which looks like ordinary web traffic, and the relay forwards between them. pooled.run has one set up (Cloudflare's TURN service), so rooms use it on their own. There is nothing to configure.

## How it works

- **Each device asks the site for the relay.** When it opens or joins a room, the page sends `POST /api/turn` and gets the relay's addresses and a credential that expires after 6 hours. It fetches a fresh one at 3/4 of that. No long-lived secret is in the page, a join link or a QR code.
- **Links still go direct whenever they can.** The browser tries direct paths first and uses the relay only when none of them works. On a home network you won't notice it.
- **Model weights never go through the relay.** A device can usually take its layers from another device's cache, which can move several GB. On a relayed link it downloads them from Hugging Face instead, and both sides enforce this. Only token traffic crosses the relay, a few KB per token per hop.
- **A relay you set yourself wins.** A relay in the **Network** box under the join form, `?turn=`, or `window.TURN_SERVERS` on a self-hosted site replaces the site's relay, and then `/api/turn` isn't called. See [TURN relay](/docs/self-host/turn).
- **If the site's relay doesn't answer** within 2.5 s, or isn't configured, the room works as before, with direct links only.

A relay adds a hop to every token's round trip, so a relayed room is slower than a direct one. In the test for PR #259, a room with every link on a relay decoded Qwen3 1.7B at 33 tok/s.

## See whether you're on the relay

- The room log says `link to laptop goes through the relay (TURN over TLS); model weights never go over it`. It names how this device reaches the relay: UDP, TCP or TLS.
- `pooledDebug()` in the browser console shows each link's `path` (`direct` or `relay`) and `via` (`udp`, `tcp` or `tls`).
- `pooledNet()` shows this tab's relay (`from`: `default` for the site's, `yours`, or `site`) and whether UDP gets out of this network.

## URL options

| Option | Effect |
|---|---|
| `?relay=1` | Sends every link through the relay, the site's included. The other devices never see this device's IP address. |
| `?relay=0` | Never asks for the site's relay. |
| `?turnapi=1` | On `localhost`, asks `/api/turn` anyway (a local static server has none, so it isn't asked by default). |

## When it still fails

Each device checks whether UDP gets out of its network. A join that found the room but got no path says why:

| You see | What to do |
|---|---|
| Found the room, but could not connect, not even through the relay (TURN) server. This network may block it too (some work networks only let web traffic out). Try another network, or set up your own relay under Network. | Try a phone hotspot. |
| Found the room, but could not connect, not even through the relay (TURN) server. Check its address and password under Network, or try another network. | Your own relay (from the Network box or `?turn=`) didn't work. Check it. |
| Found the room, but this network blocks direct (UDP) connections and there is no relay (TURN) server to go around it. Add one under Network below, or try another network (a phone hotspot works). | Shown when no relay is available, for example on a self-hosted site without one. |

A host on a network that blocks UDP sees one of these when it opens the room:

- With a relay: "This network blocks direct (UDP) connections, so links to devices on other networks go through the relay."
- Without one: "This network seems to block direct (UDP) connections and no relay (TURN) server is set, so only devices on this same network can connect. Add a relay under Network, or see Rooms at work."

What a relay can't fix:

- A network that blocks TLS to the relay's host, or only lets traffic out through an HTTP proxy that needs a login. Try a phone hotspot.
- A blocked signaling server (next section).

## Signaling at work

Before devices can link, they find each other through the signaling server: by default the public PeerJS cloud (`wss://0.peerjs.com:443`). That is an ordinary TLS WebSocket on port 443, so most work networks allow it. Filters that block uncategorized hosts or WebSockets, or TLS inspection that breaks WebSockets, can still stop it. Then the join fails at once with "Can't reach the signaling server".

The fix is a signaling server of your own on a host the network allows, passed as `?signal=` or listed in `window.POOLED_SIGNAL_SERVERS`. See [Signaling servers](/docs/self-host/signaling). A room that is already running doesn't need signaling.

## On your own deployment

A self-hosted copy of the site gets the same relay once you set a provider in its Vercel environment: a Cloudflare TURN key (`TURN_KEY_ID` and `TURN_KEY_API_TOKEN`) or your own coturn (`TURN_SECRET` with `TURN_HOST` or `TURN_URLS`). Without either, `/api/turn` answers 204 and rooms use direct links only. Setup, limits and cost: [TURN relay](/docs/self-host/turn#the-sites-relay-apiturn). The variables: [Environment and globals](/docs/reference/environment#turn-relay-apiturn).
