Most rooms never need a relay. Devices find a direct path with public STUN servers, and that works on most home and office networks. When it doesn't, a TURN relay forwards the traffic between the two devices.

pooled.run provides a relay: each device gets short-lived credentials from `POST /api/turn` and uses the relay only when no direct path works. See [Rooms at work](/docs/rooms/at-work) for what that looks like in a room, and [The site's relay](#the-sites-relay-apiturn) below for how it is set up on a deployment. No relay credentials ship in the page.

You can also bring your own relay (for example [coturn](https://github.com/coturn/coturn)) or a provider's. A relay you set replaces the site's.

## When you need it

You need a relay when no direct path exists between two devices. That happens when:

- both sides are behind symmetric NAT or carrier-grade NAT (common on mobile data), or
- a firewall blocks UDP.

The join screen tells you. After 15 s it shows "Found the room; still looking for a path between the two devices…" while the devices are still checking paths, for up to 40 s in all. If no path turns up, the join fails with:

> Found the room, but these two devices can't reach each other (a strict firewall or mobile network on one side). A relay (TURN) server gets around that: add one under Network below. Or put both on the same Wi-Fi, or try another network.

On pooled.run the site's relay usually prevents this. You see that message when no relay is available, for example on a self-hosted site without one; when UDP is blocked outright it says "this network blocks direct (UDP) connections and there is no relay (TURN) server" instead. When it happens, the **Network** box under the join form opens so you can add a relay.

If a relay was used and the join still fails, the message says so: "Found the room, but could not connect, not even through the relay (TURN) server." It then tells you to check your relay's address and password (a relay you set), or that the network may block the relay too (the site's). All the messages are in [Rooms at work](/docs/rooms/at-work#when-it-still-fails).

:::tip
Try the easy fix first. Putting both devices on the same Wi-Fi usually gives a direct path, and a direct path is faster.
:::

## Use your own relay

There are three ways to set your own relay. A relay in the URL wins over the one saved in the Network box. `window.TURN_SERVERS` is always added on top of either. When any of them is set, the page doesn't ask `/api/turn` for the site's relay.

<Tabs>
  <TabItem label="Network box">
    Under the join form, open **Network** and fill in:

    - **Relay server URL**: `turn:relay.example.org:3478`, or `turns:` for TLS. Comma-separate several.
    - **Username** and **Password**.

    Press **Save**. The setting is saved in this browser only. **Remove** clears it.
  </TabItem>
  <TabItem label="URL">
    Add the relay to the room URL. This overrides a saved setting.

    ```text
    https://pooled.run/room?turn=turn:relay.example.org:3478&turnuser=NAME&turncred=PASSWORD
    ```
  </TabItem>
  <TabItem label="Your deployment">
    If you [deploy the site yourself](/docs/self-host/deploy), define `window.TURN_SERVERS` before `room.js` loads. It is an array of standard [`RTCIceServer`](https://developer.mozilla.org/en-US/docs/Web/API/RTCIceServer) objects.

    ```html title="p2p.html"
    <script>
      window.TURN_SERVERS = [
        { urls: "turns:relay.example.org:5349", username: "pooled", credential: "CHANGE_ME" }
      ];
    </script>
    ```

    These servers are added on top of a relay set in the URL or the Network box.
  </TabItem>
</Tabs>

Relay URLs look like `turn:host[:port]` or `turns:host[:port]`, optionally followed by `?transport=udp` or `?transport=tcp`. Put the username and password in their own fields, never in the URL. An invalid URL is dropped and the rest still work.

### Relay only

By default the browser still prefers a direct path and only falls back to the relay when it has to.

Check **Always go through the relay** in the Network box (or add `?relay=1` to the URL) to use only the relay. The other devices then never see this device's IP address. `?relay=1` also forces a relay that was saved in the Network box without the checkbox.

`?relay=1` applies to whichever relay the page has: one from the URL, the Network box, `window.TURN_SERVERS` or the site's `/api/turn`. `?relay=0` stops the page from asking for the site's relay.

### Who needs it configured

With the site's relay, every device has it already. A relay of your own is set per device: every device that can't connect directly needs it. A device on an open network can reach a relayed device without it.

:::note[Join links never carry the relay]
Invite links and QR codes never include `turn`, `turnuser`, `turncred` or `relay`, so a relay password doesn't end up in a chat or a QR code. Send the relay details to the people who need them separately.
:::

## Check that it works

- Run `pooledDebug()` in the browser console. Each link shows its `path` (`direct` or `relay`) and `via` (`udp`, `tcp` or `tls`).
- The room log notes relayed links, for example "link to laptop goes through the relay (TURN over TLS); model weights never go over it".
- `pooledNet()` shows where this tab's relay comes from (`default` for the site's, `yours`, `site`) and whether UDP gets out.

A relay adds a hop to every token's round trip, so answers come slower through it than over a direct path. In the test for PR #259 (3 Chromium tabs on one machine, Qwen3 1.7B, every direct path blocked), all links used the relay and ran at 33 tok/s. Over a real network the extra hop costs more.

## The site's relay (/api/turn)

This is how pooled.run provides its relay, and how a deployment of your own can do the same ([Deploy](/docs/self-host/deploy)).

`api/turn.mjs` is a Vercel Function. `POST /api/turn` returns `iceServers` with credentials that expire. The page asks for them when it opens or joins a room, and again at 3/4 of their lifetime. With no provider set, the endpoint answers `204` and rooms use direct links only, exactly as before.

- **Model weights never go over it.** A device whose link to a weight source is relayed (or not known to be direct while a relay is set) downloads those layers from Hugging Face instead, and the other side refuses to send them over a relayed link. Only token traffic, a few KB per token per hop, crosses the relay.
- **Only this site's pages may ask.** `POST` only, and the browser's `Origin` must be the deployment's own (previews included) or listed in `TURN_ALLOWED_ORIGINS`. Anything else gets `403`.
- **Nothing secret in the page.** The provider's key stays in the Vercel environment and never appears in a response or a log.

### Set up Cloudflare TURN (what pooled.run uses)

Cloudflare's TURN service is anycast and listens on UDP and TCP 3478 and TLS 443. The first 1,000 GB a month are free, then $0.05 per GB.

<Steps>

1. In the [Cloudflare dashboard](https://dash.cloudflare.com), open **Realtime → TURN Server** and create a TURN key. Copy the **Turn Token ID** and the **API Token**. The token is shown only once. See [Cloudflare's docs](https://developers.cloudflare.com/realtime/turn/).

2. In the Vercel project, go to **Settings → Environment Variables** and add these for Production and Preview:

   - `TURN_KEY_ID`: the Turn Token ID
   - `TURN_KEY_API_TOKEN`: the API Token (mark it Sensitive)

3. Redeploy production. Environment variables reach only new deployments.

4. Check it:

   ```sh
   curl -si -X POST -H 'Origin: https://pooled.run' https://pooled.run/api/turn
   ```

   `200` with `iceServers` means it works. `204` means the variables aren't set on that deployment. Then open a room with `?relay=1` on two devices: the room log should say "goes through the relay (TURN over …)".

</Steps>

Port-53 URLs from Cloudflare are dropped, because browsers block port 53.

### Or your own coturn

Run coturn in `use-auth-secret` mode (the TURN REST API), with TLS on 443 for the strictest firewalls:

```ini title="/etc/turnserver.conf"
listening-port=3478
tls-listening-port=443
cert=/etc/letsencrypt/live/relay.example.org/fullchain.pem
pkey=/etc/letsencrypt/live/relay.example.org/privkey.pem
use-auth-secret
static-auth-secret=<a long random string>
realm=relay.example.org
no-multicast-peers
denied-peer-ip=10.0.0.0-10.255.255.255
denied-peer-ip=172.16.0.0-172.31.255.255
denied-peer-ip=192.168.0.0-192.168.255.255
total-quota=200
bps-capacity=0
```

Then set these in Vercel instead of the Cloudflare variables:

- `TURN_SECRET`: the same `static-auth-secret`;
- `TURN_HOST=relay.example.org`, which hands out `turn:relay.example.org:3478` over UDP and TCP and `turns:relay.example.org:443`. Or set `TURN_URLS` to your own comma-separated list.

The function signs `<expiry>:pooled` with HMAC-SHA1 of the secret, and coturn refuses a credential after its expiry. If both providers are set, Cloudflare wins. (The long-term user setup in [Run your own with coturn](#run-your-own-with-coturn) is for relays you type into the Network box; this one is for the site's relay.)

### Optional settings

| Variable | Default | Meaning |
|---|---|---|
| `TURN_TTL` | `21600` (6 h) | Credential lifetime in seconds, 600 to 86400. The page fetches new ones at 3/4 of it. |
| `TURN_RATE` | `10` | Credential requests per minute per IP, per function instance. |
| `TURN_ALLOWED_ORIGINS` | none | Other origins allowed to ask, comma-separated. `*` matches within one host label (`https://pooled-*.vercel.app`). The deployment's own origin is always allowed. |

### Abuse and cost

Anyone who can call `/api/turn` gets a working credential until it expires, and relayed bytes cost money. The `Origin` check stops other websites from minting credentials in their visitors' browsers. It doesn't stop a script, which can forge any header, so:

- credentials are short-lived (`TURN_TTL`);
- there is a per-IP limit (`TURN_RATE`). It is kept per function instance, so it slows abuse down but isn't a hard limit. For one, add a Vercel Firewall rule: **Firewall → Rules →** path equals `/api/turn` **→ Rate limit**, for example 20 requests per minute per IP;
- set a spending cap or usage alert with the provider.

## Run your own with coturn

[coturn](https://github.com/coturn/coturn) is an open-source TURN server. Run it on a machine with a public IP address.

<Steps>

1. Install coturn.

   <Tabs>
     <TabItem label="Debian / Ubuntu">
       ```sh
       sudo apt install coturn
       ```
     </TabItem>
     <TabItem label="Docker">
       ```sh
       docker pull coturn/coturn
       ```
     </TabItem>
   </Tabs>

2. Write a config with one long-term user. Pooled passes a fixed username and password, so use `lt-cred-mech`. The Debian and Ubuntu package reads `/etc/turnserver.conf`. For Docker, put it at `/etc/coturn/turnserver.conf` on the host; step 4 mounts it into the container.

   ```ini title="/etc/turnserver.conf"
   listening-port=3478
   tls-listening-port=5349
   realm=relay.example.org
   fingerprint
   lt-cred-mech
   user=pooled:CHANGE_ME

   # TLS for turns: (copies of your certificate and key, see below)
   cert=/etc/coturn/certs/fullchain.pem
   pkey=/etc/coturn/certs/privkey.pem

   # Ports the relay hands out to devices
   min-port=49152
   max-port=65535

   # Only if the machine is behind NAT (a cloud VM with a private address):
   # external-ip=<public IP>/<private IP>

   # Don't relay into private networks
   no-multicast-peers
   denied-peer-ip=10.0.0.0-10.255.255.255
   denied-peer-ip=172.16.0.0-172.31.255.255
   denied-peer-ip=192.168.0.0-192.168.255.255
   ```

   The key and certificate must be readable by the user coturn runs as: `turnserver` for the Debian and Ubuntu package, `nobody` in the Docker image. Let's Encrypt's `privkey.pem` is readable by root only, so copy the two files to `/etc/coturn/certs/` with permissions coturn can read (for example from a certbot deploy hook), and copy them again after each renewal.

3. Open the firewall: 3478 UDP and TCP, 5349 TCP (for `turns:`), and UDP 49152 to 65535 for the relayed traffic.

4. Start it.

   <Tabs>
     <TabItem label="Debian / Ubuntu">
       ```sh
       sudo systemctl enable --now coturn
       ```

       The systemd unit runs `turnserver -c /etc/turnserver.conf` as the `turnserver` user. `TURNSERVER_ENABLED=1` in `/etc/default/coturn` is read only by the old init script, so systemd doesn't need it.
     </TabItem>
     <TabItem label="Docker">
       ```sh
       docker run -d --name coturn --network=host \
         -v /etc/coturn/turnserver.conf:/etc/coturn/turnserver.conf:ro \
         -v /etc/coturn/certs:/etc/coturn/certs:ro \
         coturn/coturn -c /etc/coturn/turnserver.conf --log-file=stdout
       ```

       `docker logs coturn` shows the log. Run `docker restart coturn` after changing the config.
     </TabItem>
   </Tabs>

5. Point devices at it with any of the three ways above, for example:

   ```text
   ?turn=turns:relay.example.org:5349,turn:relay.example.org:3478&turnuser=pooled&turncred=CHANGE_ME
   ```

6. Join a room and run `pooledDebug()`. With **Always go through the relay** checked, every link should show `path: "relay"`.

</Steps>

:::caution
Anyone with the username and password can use your relay's bandwidth. Share them only with people in your rooms, and change the password if it leaks.
:::

## Test it

The repo has a minimal TURN server for tests (`tests/e2e/turn_server.mjs`: UDP, loopback only, not for real use). This test runs a room on one machine with every direct path dropped. It checks that the join fails without a relay and works through one:

```sh
node tests/e2e/room_chaos.mjs --devices 3 --plan turn --nomodel   # without a model
node tests/e2e/room_chaos.mjs --devices 3 --plan turn             # also runs answers (Qwen3 1.7B by default)
```

It needs `npm install` (Playwright and the `peer` server). The run with a model loads it on WebGPU, so it needs a GPU.

The site's relay has its own tests: `tests/unit/turn_api_test.js` (the function: both providers, the origin check, the rate limit, not configured), `tests/unit/ice_test.js` (the client, including the weights-over-relay decision), and `tests/e2e/room_relay.mjs`, which runs two tabs with UDP turned off in Chromium, `?relay=1`, credentials from the real `api/turn.mjs` and a local coturn over TCP and TLS.
